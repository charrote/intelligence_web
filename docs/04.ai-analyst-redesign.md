## 1. 重构背景与目标

### 1.1 问题陈述

当前 AI 分析师功能（`core/app.py` 第 1241-1582 行）采用 **实时同步问答** 模式：

```
用户提问 → HTTP 同步等待 LLM（超时 90s）→ 返回结果
```

经过数月的服务器和模型验证，该模式存在以下根本性问题：

| 问题 | 现象 | 根因 |
|------|------|------|
| **高并发不稳定** | 多个用户同时提问时，响应质量急剧下降 | 模型推理资源有限，无法处理并发 |
| **强逻辑推理失败** | 复杂分析问题时返回不完整或错误的推理 | 模型能力不足以支撑实时逻辑推理 |
| **长时间无响应** | 前端等待 90s 超时后仅显示空结果 | 同步阻塞模式下网络延迟 + 推理时间不可控 |

### 1.2 重构目标

**核心方向：从实时问答转为离线定时报告生成。**

| 维度 | 重构前 | 重构后 |
|------|--------|--------|
| 触发方式 | 用户即时提问 | 定时后台执行 |
| 用户交互 | 等待 LLM 返回（可能 90s+） | 查看已生成的报告（毫秒级） |
| LLM 调用频率 | 用户每次提问一次（高频、随机时间） | 每日固定时间（低频、可控） |
| 模型压力 | 不可控的突发并发 | 单线程串行执行，零并发 |
| 结果可靠性 | 因超时和质量不稳定 | 有充足时间完成推理，质量更高 |
| 失败处理 | 超时则空结果 | 重试 + 熔断 + 告警 |

### 1.3 功能定位

重构后的 AI 分析师是 **定时情报报告系统**，不是实时问答系统。

**目标用户场景：**
- 竞争对手客户体系分析（每日更新）
- 各国产品总容量统计（每日更新）
- 各产品市场主要生产厂商及市场份额（每日更新）
- 新情报分类摘要（每日更新）

## 2. 总体架构

### 2.1 架构总览

```
┌────────────────────────────────────────────────────────────────────┐
│                     intelligence_web 容器 (:8766)                    │
│                                                                    │
│  ┌──────────────────────────────────────────────────────────┐     │
│  │                  Flask API 进程                            │     │
│  │  ┌────────────────────────────────────────────────────┐  │     │
│  │  │  HTTP 路由层 (core/app.py)                          │  │     │
│  │  │  - GET /api/reports/templates      报告模板 CRUD   │  │     │
│  │  │  - GET /api/reports/runs/{tid}      执行历史        │  │     │
│  │  │  - POST /api/reports/run/{tid}     手动触发执行     │  │     │
│  │  │  - GET /api/reports/runs/{rid}     单次报告详情     │  │     │
│  │  │  - GET /api/reports/scheduler      调度器状态       │  │     │
│  │  │  - POST /api/reports/scheduler/toggle  开关调度     │  │     │
│  │  └────────────────────────────────────────────────────┘  │     │
│  │                                                          │     │
│  │  处理 HTTP 请求，不执行报告生成                             │     │
│  └──────────────────────────────────────────────────────────┘     │
│                                                                    │
│  ┌──────────────────────────────────────────────────────────┐     │
│  │              调度器进程 (scheduler.py)                      │     │
│  │                                                          │     │
│  │  APScheduler BackgroundScheduler                         │     │
│  │  每 5 分钟触发一次 → run_scheduled_reports()             │     │
│  │                                                          │     │
│  │  执行流程：                                                │     │
│  │  [1] 读取 enabled=True 且 next_run ≤ now 的模板          │     │
│  │  [2] 按 domain 分组                                      │     │
│  │  [3] 调用对应域 API 检索情报数据                          │     │
│  │  [4] 用 Jinja2 渲染 prompt 模板                          │     │
│  │  [5] POST 到 LLM API（120s 超时，最多重试 1 次）          │     │
│  │  [6] 解析响应，存入 report_run 表                        │     │
│  │  [7] 更新 next_run，计算 fail_count（熔断逻辑）           │     │
│  │                                                          │     │
│  │  失败处理：                                                │     │
│  │  - 第 1 次失败 → 1 分钟后重试 1 次                       │     │
│  │  - 重试仍失败 → fail_count += 1                          │     │
│  │  - fail_count >= 3 → 标记 fused，停止自动重试            │     │
│  │  - 成功后 → fail_count 归零                              │     │
│  │  - 用户手动强制触发 → 绕过熔断                            │     │
│  └──────────────────────────────────────────────────────────┘     │
│                                                                    │
│  ┌──────────────────────────────────────────────────────────┐     │
│  │              SQLite 数据库（共享）                          │     │
│  │  - report_template（报告模板）                             │     │
│  │  - report_run（执行记录）                                  │     │
│  │  - report_scheduler（调度器状态）                          │     │
│  └──────────────────────────────────────────────────────────┘     │
└────────────────────────────────────────────────────────────────────┘
```

### 2.2 为什么调度器部署在 intelligence_web 容器中

| 方案 | 优点 | 缺点 | 结论 |
|------|------|------|------|
| 嵌入 Flask 主进程 | 零新进程 | APScheduler 与 HTTP 线程争抢，可能阻塞请求 | ❌ 不推荐 |
| **独立后台进程（同容器）** | 零新容器，共享数据库，不阻塞 HTTP | 需管理进程生命周期 | ✅ **推荐** |
| 独立新容器 | 完全隔离 | 需修改 docker-compose，增加运维成本 | ❌ 过度设计 |
| 外部系统 cron | 最简单 | 无法监控状态，无法处理失败重试 | ❌ 不可控 |

**结论：** 在 `intelligence_web` 容器中增加一个独立调度器进程（`scheduler.py`），与 Flask API 同容器运行，共享 SQLite 数据库。通过 `docker-compose` 的 `depends_on` 确保启动顺序。

### 2.3 调度器执行时序图

```
[T=0]  APScheduler 触发 run_scheduled_reports()
    │
    ▼
[T+0s]  SELECT * FROM report_template
        WHERE enabled=1 AND next_run <= now()
        AND status NOT IN ('fused')
    │
    ▼  假设查询到 3 个模板（2 个研究域，1 个销售域）
    │
[T+1s]  按 domain 分组：
        - 研究域: [市场份额概览, 新情报摘要]
        - 销售域: [竞争对手动态]
    │
    ▼
[T+2s]  串行执行每个报告（同一域之间串行，不同域可并行但简化处理，统一串行）
    │
    ├── [研究域 - 市场份额概览]
    │   ├── POST intelligence_web:8766/api/intelligence/query (搜索近30天数据)
    │   ├── 构建统计摘要（按厂商计数）
    │   ├── Jinja2 渲染 prompt（替换变量：日期范围、数据摘要）
    │   ├── POST LLM API（120s 超时）
    │   │   ├── 成功 → 解析 response → 存入 report_run
    │   │   └── 失败 → 等待 60s → 重试 1 次
    │   │       ├── 重试成功 → 存入 report_run
    │   │       └── 重试失败 → fail_count += 1，检查是否熔断
    │   └── UPDATE report_template SET next_run = now() + interval
    │
    ├── [研究域 - 新情报摘要] ...（同上流程）
    │
    └── [销售域 - 竞争对手动态]
        └── POST intelligence_sales:8767/api/intelligence/query ...（同上）
    │
    ▼
[T+N*120s]  所有报告执行完毕
```

**关键参数：**

| 参数 | 值 | 说明 |
|------|-----|------|
| 调度器轮询间隔 | 每 5 分钟 | 检查是否有到期报告需要执行 |
| 单次 LLM 调用超时 | 120 秒 | 比当前 90s 宽裕 30%，减少超时概率 |
| 首次失败重试间隔 | 60 秒 | 短暂等待后重试，给模型恢复机会 |
| 最大重试次数 | 1 次 | 失败后重试 1 次，仍失败则停止 |
| 熔断阈值 | 连续失败 3 次 | 超过后标记 fused，需人工介入 |
| 报告数据查询范围 | 近 30 天 | 可根据报告类型配置（可覆盖） |
| 报告保留期 | 30 天 | 超过后自动清理 |
| 清理执行频率 | 每 24 小时 | 调度器在每天首次执行时清理过期记录 |

### 3.4 报告状态机

```
                    ┌─────────────┐
                    │   pending   │ ← 调度器选中，等待执行
                    └──────┬──────┘
                           │
                    ┌──────▼──────┐
                    │   running   │ ← 正在检索数据/调用LLM
                    └──┬───────┬──┘
                       │       │
              ┌────────▼─┐  ┌──▼──────────┐
              │ completed │  │   failed    │ ← 首次失败
              └───────────┘  └──┬──────────┘
                                │
                        ┌───────▼───────┐
                        │  retrying     │ ← 重试中（最多1次）
                        └──┬─────────┬──┘
                           │         │
                ┌──────────▼──┐  ┌───▼────────┐
                │  completed  │  │  failed    │ ← 重试仍失败
                │ (retry ok)  │  └───┬────────┘
                └─────────────┘      │
                                  检查 fail_count
                                      │
                    ┌─────────────────┼─────────────────┐
                    ▼                               ▼
            fail_count < 3                     fail_count >= 3
            下次调度周期重试                   标记 fused
            下次成功后 fail_count 归零         停止自动重试
```

**状态定义表：**

| 状态 | 含义 | 下一步 |
|------|------|--------|
| `pending` | 调度器已选中，尚未开始执行 | 进入 running |
| `running` | 正在执行（检索数据 + LLM 调用） | 成功→completed，失败→failed |
| `completed` | 执行成功，结果已持久化 | 无 |
| `failed` | 执行失败 | 检查 fail_count，决定重试或熔断 |
| `fused` | 连续失败≥3次，自动熔断 | 需用户手动强制触发或修复后解除 |

### 7.2 核心执行逻辑

```python
def execute_report(template: dict) -> dict:
    """执行单个报告，返回 report_run 记录"""
    run = create_run_record(template)  # 状态: pending → running
    
    # Step 1: 数据检索
    intel_data = fetch_intelligence(
        domain=template["domain"],
        days=template["lookback_days"]
    )
    stats = build_statistics(intel_data)
    
    # Step 2: 渲染 prompt
    prompt = render_template(template["prompt_tmpl"], {
        "start_date": (datetime.now() - timedelta(days=template["lookback_days"])).isoformat(),
        "end_date": datetime.now().isoformat(),
        "domain": template["domain"],
        "report_name": template["name"],
        "record_count": len(intel_data),
        "stats_by_company": stats["by_company"],
        "stats_by_category": stats["by_category"],
        "stats_by_month": stats["by_month"],
        "relevant_intelligence": summarize(intel_data[:10]),
    })
    
    # Step 3: 调用 LLM（含重试）
    max_retries = 1
    for attempt in range(1 + max_retries):
        try:
            response = call_llm_api(prompt, timeout=120)
            result = parse_llm_response(response)
            break
        except Exception as e:
            if attempt == max_retries:
                raise ReportExecutionError(f"LLM 调用失败 (重试{max_retries}次): {e}")
            time.sleep(60)  # 等待 60 秒后重试
    
    # Step 4: 持久化
    save_run_output(run, result)
    update_template_next_run(template)
    reset_fail_count(template)  # 成功后归零
    return run
```

### 7.3 Prompt 渲染模块（prompt_renderer.py）

```python
def render_template(template_str: str, variables: dict) -> str:
    """使用 Jinja2 渲染 prompt 模板"""
    from jinja2 import Environment, StrictUndefined
    env = Environment(undefined=StrictUndefined)
    tmpl = env.from_string(template_str)
    return tmpl.render(**variables)
```

### 7.4 LLM 调用模块（llm_client.py）

```python
def call_llm_api(prompt: str, timeout: int = 120) -> dict:
    """调用外部 LLM API（OpenAI 兼容 / Anthropic）"""
    config = get_llm_config()  # 从 settings 读取
    
    if config["provider"] == "anthropic":
        return call_anthropic(prompt, timeout)
    else:  # OpenAI compatible
        return call_openai_compatible(prompt, timeout)

def call_openai_compatible(prompt: str, timeout: int) -> dict:
    """调用 OpenAI 兼容 API"""
    import requests
    response = requests.post(
        url=f"{config['api_base_url']}/v1/chat/completions",
        headers={"Authorization": f"Bearer {config['api_key']}"},
        json={
            "model": config["model_name"],
            "messages": [{"role": "system", "content": SYSTEM_PROMPT}, {"role": "user", "content": prompt}],
            "temperature": 0.1,  # 低温度，确保输出确定性
            "max_tokens": 2000,
        },
        timeout=timeout
    )
    response.raise_for_status()
    return response.json()
```

**关键配置说明：**

| 参数 | 值 | 理由 |
|------|-----|------|
| temperature | 0.1 | 低随机性，确保报告内容确定性，便于对比历史版本 |
| max_tokens | 2000 | 限制输出长度，避免过长推理 |
| timeout | 120s | 比当前 90s 宽裕，适应模型慢响应 |

## 11. 风险与缓解

| 风险 | 影响 | 概率 | 缓解措施 |
|------|------|------|----------|
| LLM 持续不可用 | 所有报告执行失败 | 低 | 熔断机制 + 用户告警 + 保留最近 7 次历史数据 |
| Jinja2 模板语法错误 | 报告无法生成 | 中 | 创建/编辑模板时前端做基本语法校验，执行时捕获异常 |
| 调度器进程意外退出 | 报告停止生成 | 低 | 容器 healthcheck + 自动重启；`depends_on` 确保 Flask 启动后再启动调度器 |
| SQLite 写锁竞争 | 报告写入失败 | 极低 | 调度器串行执行，Flask 只读 report_run，写入竞争极少 |
| 用户 prompt 注入 | LLM 被恶意 prompt 影响 | 中 | 所有用户输入的变量值用 `| e` (escape) 过滤；`StrictUndefined` 防止变量未定义 |
| 报告内容过时 | 用户看到旧数据 | 低 | 报告时间戳清晰展示；数据范围可配置 |
| 内置模板 Prompt 太长 | LLM 超时或输出截断 | 中 | `max_tokens=2000` 限制；prompt 模板控制在 1000 token 以内 |

### C. 与 v0.1 设计稿的差异总结

| 设计点 | v0.1 | v1.0（本稿） | 变更原因 |
|--------|------|--------------|----------|
| 调度器部署 | 未明确 | 独立进程，同容器 | 审查关键问题：避免阻塞 HTTP 线程 |
| AI 辅助创建模板 | 支持 | 移除，改为变量选择器 | 审查重要问题：与"非实时"原则矛盾 |
| 失败处理 | 简单重试 | 熔断机制 + fail_count | 审查重要问题：防止持续失败资源浪费 |
| 状态机 | 4 个状态 | 5 个状态（+retrying, +fused） | 审查建议：精确描述执行过程 |
| 内置模板存储 | 未明确 | 数据库种子数据 | 审查建议：保持数据一致性 |
| 清理策略 | 30 天未定义 | 30 天 + 每日自动清理 | 审查建议：防止数据膨胀 |
| 前端导航 | 有页面设计 | 补充完整导航路径 | 审查重要问题：导航结构缺失 |
