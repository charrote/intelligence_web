## 1. 重构背景与问题诊断

### 1.1 实时问答的三大致命问题

当前 AI 分析师功能（`core/app.py` 第 1241-1582 行）采用实时同步模式：

```
用户提问 → HTTP 同步等待 LLM（超时 90s）→ 返回结果
```

经过数月验证，三个问题无法解决：

| 问题 | 现象 | 根因 |
|------|------|------|
| 高并发不稳定 | 多用户同时提问，质量急剧下降 | 模型推理资源有限 |
| 强逻辑推理失败 | 复杂分析问题返回错误推理 | 模型能力不足以实时推理 |
| 长时间无响应 | 90s 超时后空结果 | 同步阻塞下延迟不可控 |

**结论：实时问答模式在这个硬件条件下不可行。**

---

### 1.2 情报数据的"非结构化困境"（本次发现的根本问题）

在重新审视数据层时，发现了比"实时问题"更根本的障碍。

**当前 `intelligence` 表（`core/db.py` 第 53-68 行）：**

```sql
CREATE TABLE intelligence (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    title TEXT UNIQUE NOT NULL,
    content TEXT NOT NULL,              -- ← 全量原始文本
    category TEXT DEFAULT '',
    status TEXT DEFAULT 'pending',
    opinion TEXT DEFAULT '',
    contact_name TEXT DEFAULT '',
    company TEXT DEFAULT '',
    deal_value REAL DEFAULT 0,
    industry TEXT DEFAULT '',
    project_id INTEGER,
    source_url TEXT DEFAULT '',
    created_at TEXT NOT NULL,
    updated_at TEXT NOT NULL
);
```

**一条典型情报的 `content` 内容（`inbox/` 中的原始文件）：**

```
来源：Bassetti Group
关键数字：4.9B 美元市场预测（软件定义机电一体化产品）
关键数字：65% 的 G1000 制造商将使用 AI 代理
关键时间：到 2028 年
产品：SDMPs（软件定义机电一体化产品）
报告来源：Gartner
```

**问题：所有结构化信息都淹没在 `content` 文本中。**

```sql
-- 这些查询全部失效：
SELECT * FROM intelligence WHERE deal_value > 1000000000;    -- 查不到 4.9B
SELECT * FROM intelligence WHERE entity_type = 'competitor'; -- 没有这个字段
SELECT company, COUNT(*) FROM intelligence GROUP BY company; -- company 几乎全为空
```

**这意味着：报告系统无法直接通过 SQL 进行任何有意义的聚合。**

如果报告系统必须让 LLM 每次重新读取 `content` 文本来提取数据，那就又回到了"实时推理"的老路——而这正是我们试图解决的问题。

---

### 1.3 根本解决方案：非实时 AI 抽取 + 结构化存储

**核心思路：把 AI 的调用从"报告推理阶段"提前到"情报采集阶段"。**

```
旧模式（问题）：
  Agent 采集原始文本 → 存 intelligence 表 → 用户查询 → LLM 实时推理文本 → 空结果或错误

新模式（方案）：
  Agent 采集原始文本 → 存 intelligence 表 → [AI 离线抽取] → intel_fact 表 → 用户查询 → SQL 聚合 + LLM 文字总结 → 报告
```

**关键差异：**

| 维度 | 旧模式 | 新模式 |
|------|--------|--------|
| AI 调用时机 | 用户查询时（实时） | 情报采集后（离线，非实时） |
| AI 调用次数 | 每次查询一次（不可控） | 每批情报一次（可控） |
| AI 任务复杂度 | 复杂逻辑推理 | 简单字段提取 |
| AI 失败影响 | 用户无法获取报告 | 部分情报无结构化数据，报告仍有部分数据 |
| 数据可查询性 | 不可（全是文本） | 可（结构化的 key-value 对） |
| 报表灵活性 | 不可（依赖 LLM 每次推理） | 高（SQL 聚合 + 可配置规则） |

---

### 1.4 功能定位

重构后的 AI 分析师是 **离线情报结构化 + 定时报告生成系统**。

**目标用户场景：**
- 竞争对手客户体系分析（每日更新）
- 各国产品总容量统计（每日更新）
- 各产品市场主要生产厂商及市场份额（每日更新）
- 新情报分类摘要（每日更新）

## 2. 四层架构设计

### 2.1 架构总览

```
┌──────────────────────────────────────────────────────────────────────────────┐
│                       intelligence_web 容器 (:8766)                           │
│                                                                             │
│  ┌───────────────────────────────────────────────────────────────────────┐  │
│  │                          Flask API 进程                                │  │
│  │  处理 HTTP 请求，不执行数据抽取或报告生成                                │  │
│  └───────────────────────────────────────────────────────────────────────┘  │
│                                                                             │
│  ┌───────────────────────────────────────────────────────────────────────┐  │
│  │                      调度器进程 (scheduler.py)                          │  │
│  │  APScheduler BackgroundScheduler（每 5 分钟触发一次）                   │  │
│  │                                                                       │  │
│  │  ┌────────────────────────────────────────────────────────────────┐   │  │
│  │  │  流程 A: 情报结构化抽取（每 10 分钟触发）                         │   │  │
│  │  │  1. 查找未抽取的新情报（extracted=0）                            │   │  │
│  │  │  2. 读取所有 enabled 的抽取规则                                   │   │  │
│  │  │  3. 对每条情报 × 每个规则：                                      │   │  │
│  │  │     a. 构造抽取 Prompt（字段列表 + 情报内容）                     │   │  │
│  │  │     b. POST 到 LLM API（60s 超时）                               │   │  │
│  │  │     c. 解析 JSON 响应，存入 intel_fact 表                       │   │  │
│  │  │     d. 标记情报 extracted=1                                       │   │  │
│  │  └────────────────────────────────────────────────────────────────┘   │  │
│  │                                                                       │  │
│  │  ┌────────────────────────────────────────────────────────────────┐   │  │
│  │  │  流程 B: 定时报告生成（每 5 分钟触发）                            │   │  │

│  │  │  3. Jinja2 渲染 Prompt（含聚合数据）                             │   │  │
│  │  │  4. LLM 生成文字分析（轻量，不涉及逻辑推理）                      │   │  │
│  │  │  5. 存入 report_run 表                                           │   │  │
│  │  └────────────────────────────────────────────────────────────────┘   │  │
│  │                                                                       │  │
│  │  失败处理：                                                            │  │
│  │  - 抽取失败 → 标记情报 extracted=failed，下次轮询重试                  │  │

│                                                                             │
│  ┌───────────────────────────────────────────────────────────────────────┐  │
│  │                        SQLite 数据库（共享）                           │  │
│  │                                                                       │  │
│  │  Layer 1: intelligence（原始情报，不变）                               │  │
│  │  Layer 2: intel_extraction_rule + intel_extraction_field（抽取规则）   │  │
│  │  Layer 3: intel_fact（结构化事实）                                     │  │
│  │  Layer 4: intel_aggregate + report_run（报告模板 + 执行记录）           │  │
```

### 2.2 四层架构详解

#### Layer 1 — 原始情报层

```
intelligence 表
├── title      ← 情报标题（唯一，去重）
├── content    ← 全量原始 markdown 文本
├── category   ← 分类
├── company    ← 公司名（已有，但利用率低）
├── source_url ← 来源链接
└── ...（其他 10 个字段）
```

**角色：** 原始情报的存储锚点。AI 采集的外部 Agent（cron 每小时）写入此表。  
**是否修改：** 不修改。作为系统底层不变的数据基础。

---

#### Layer 2 — 抽取规则层（用户配置）

```
intel_extraction_rule ────── 1:N ────── intel_extraction_field
│                                      │
│  id, domain, name, description      │  id, rule_id, field_key, field_label
│  scope, max_fields, enabled         │  field_type, is_required, default_value
│  created_at, updated_at             │  sort_order
```

**角色：** 用户通过前端表单定义"每次采集情报时，从中提取哪些字段"。  
**是否修改：** **新增两张表。** 这是本设计的核心创新。

**用户配置示例：**

```
规则名称: 厂商市场数据
域名:     research（研究域）
抽取范围: 全文
最大字段数: 10

字段列表:
  #1  厂商名称    [company]       公司名     必填
  #2  市场份额    [pct]           百分比     可选
  #3  市场规模    [currency]      金额       可选
  #4  币种        [currency_code] 货币代码   可选
  #5  国家/地区   [location]      地点       可选
  #6  年份        [year]          年份       可选
  #7  增长率      [pct]           百分比     可选
  #8  数据来源    [text]          文本       可选
```

---

#### Layer 3 — 结构化事实层

```
intel_fact 表
├── id              INTEGER PK
├── intel_id        INTEGER  FK → intelligence.id   （锚定原始情报）
├── rule_id         INTEGER  FK → intel_extraction_rule.id  （关联抽取规则）
├── field_key       TEXT     字段标识（来自规则定义）
├── entity_name     TEXT     实体名称（如厂商名、公司名）
├── metric_name     TEXT     指标名称（如"市场份额"、"增长率"）
├── metric_value    REAL     数值（如 35.0）
├── metric_unit     TEXT     单位（如 "%"、"USD"、"亿"）
├── time_period     TEXT     时间范围（如 "2026"、"2025-2026"）
├── context         TEXT     补充上下文（如 "中国 MES 市场"）
├── source_anchor   TEXT     原始文本中的定位锚点
├── confidence      TEXT     置信度：high / medium / low
├── created_at      DATETIME 抽取时间
```

**设计原则：**
- **表结构永远不变** — 所有动态字段存入 `field_key` + `entity_name` + `metric_value`
- **一条情报 → 多条事实** — 一条情报可同时被多个规则抽取，产生多条 `intel_fact`
- **宽表 + key-value 混合** — 固定字段存类型信息，动态字段存 key-value

**存储示例（一条情报 → 抽取 4 条事实）：**

```
intel_id=100, rule_id=3, field_key="厂商名称",   entity_name="Siemens",     metric_name=null,    metric_value=null,      ...
intel_id=100, rule_id=3, field_key="市场份额",   entity_name=null,          metric_name="市场份额", metric_value=35.0,    metric_unit="%"
intel_id=100, rule_id=3, field_key="国家/地区",  entity_name="中国",        metric_name=null,    metric_value=null,      ...
intel_id=100, rule_id=3, field_key="年份",       entity_name=null,          metric_name="年份",   metric_value=2026.0,   metric_unit="年"
```

---

#### Layer 4 — 报告模板层（用户配置）

```
intel_aggregate 表
├── id              INTEGER PK
├── domain          TEXT     域标识
├── name            TEXT     报告名称
├── description     TEXT     描述
├── rule_id         INTEGER  FK → intel_extraction_rule.id   ← 关联抽取规则
├── group_by        TEXT     聚合维度: entity_name / time_period / context
├── metrics         JSON     聚合指标配置: [{"field_key":"市场份额","agg":"avg","label":"平均市场份额"}]
├── filters         JSON     过滤条件: [{"field_key":"国家/地区","op":"eq","value":"中国"}]
├── chart_config    JSON     图表配置: [{"type":"pie","title":"市场份额","data_field":"metrics[0]"}]
├── prompt_template TEXT     LLM 文字分析 Prompt（Jinja2 模板）
├── schedule_minutes INTEGER 执行间隔（分钟）
├── lookback_days   INTEGER  数据查询范围（天）
├── enabled         BOOLEAN  是否启用
├── next_run        DATETIME 下次执行时间
├── status          TEXT     active / fused
├── fail_count      INTEGER  连续失败次数
├── last_fail_time  DATETIME
├── last_success_time DATETIME
├── built_in        BOOLEAN  是否内置模板
├── created_at, updated_at
```

**关键设计：** 报告模板 **直接关联抽取规则**（`rule_id`），不再需要单独的 `chart_config` 字段存"图表应该长什么样"—— 图表的数据源直接来自 `intel_fact` 表的聚合结果。

---

### 2.3 为什么四层分离能应对"多变需求"

| 用户操作 | 需要改代码吗？ | 在哪层操作？ |
|----------|:------------:|:---------:|
| 新增抽取字段 | 不需要 | Layer 2 — 编辑抽取规则 |
| 修改聚合维度 | 不需要 | Layer 4 — 编辑报告模板 |
| 新增图表类型 | 不需要 | Layer 4 — 编辑 chart_config |
| 新增报告 | 不需要 | Layer 4 — 新建报告模板 |
| 新增抽取规则 | 不需要 | Layer 2 — 新建抽取规则 |
| 修改 Prompt 模板 | 不需要 | Layer 4 — 编辑 prompt_template |

**所有配置全部存在 SQLite 中，重启不丢失，用户通过前端表单即可完成所有变更。**

## 3. 数据模型

### 3.1 intelligence（现有表，不修改）

保持不变。作为系统底层不变的数据基础。

### 3.2 intel_extraction_rule（新表）

| 字段 | 类型 | 约束 | 说明 |
|------|------|------|------|
| id | INTEGER | PK, AUTOINCREMENT | 主键 |

### 3.3 intel_extraction_field（新表）

## 4. 数据流

### 4.1 数据流总览

```
[外部 Agent]
  cron 每小时采集情报
  │
  ▼
[1. 存入 intelligence 表]  ← 现有流程，不变
  title, content, source_url ...
  │
  ▼
[2. 标记为未抽取]  intelligence.extracted = 0
  │
  ▼
[调度器 - 抽取任务 每 10 分钟触发]
  │
  ▼
[3. 查找未抽取的情报]
  SELECT * FROM intelligence WHERE extracted = 0
  │
  ▼
[4. 读取所有 enabled 的抽取规则]
  SELECT * FROM intel_extraction_rule WHERE enabled = 1
  │
  ▼
[5. 对每条情报 × 每个规则]
  │   a. 读取该规则的字段列表
  │   b. 构造抽取 Prompt
  │   c. POST 到 LLM API（60s 超时）
  │   d. 解析 JSON 响应
  │   e. 写入 intel_fact 表（每条字段 → 一行）
  │   f. 标记 intelligence.extracted = 1
  │
  ▼
[6. 更新 intel_fact 表的索引（自动，SQLite）]
  │
  ▼
[7. 更新 report_scheduler.last_extract_time]
```

### 4.3 定时报告生成流

```
[调度器 - 报告任务 每 5 分钟触发]
    │
    ▼
[1. 查找到期模板]
    SELECT * FROM intel_aggregate
    WHERE enabled = 1 AND next_run <= now() AND status != 'fused'
    │
    ▼
[2. 执行 SQL 聚合]
    ─────────────────────────────────────────────────────────
    根据模板配置动态构建 SQL：

    示例（市场份额概览模板）：
    ┌────────────────────────────────────────────────────┐
    │  group_by = entity_name                            │
    │  metrics = [{field_key:"market_share", agg:"avg"}] │
    │  filters = []                                      │
    │  lookback_days = 30                                │
    └────────────────────────────────────────────────────┘

    生成的 SQL:
    SELECT f.entity_name,
           AVG(f2.metric_value) AS avg_market_share
    FROM intel_fact f
    JOIN intel_fact f2 ON f.intel_id = f2.intel_id
                       AND f.rule_id = f2.rule_id
    WHERE f.field_key = 'company_name'
      AND f2.field_key = 'market_share'
      AND f.rule_id = {template.rule_id}
      AND f.created_at >= datetime('now', '-30 days')
      {filters SQL clause}
    GROUP BY f.entity_name
    ORDER BY avg_market_share DESC

    返回结果:
    [{"entity_name": "Siemens", "avg_market_share": 35.2},
     {"entity_name": "Rockwell", "avg_market_share": 24.8},
     ...]
    ─────────────────────────────────────────────────────────
    │
    ▼
[3. 构建图表数据]
    ─────────────────────────────────────────────────────────
    根据 chart_config 配置，将聚合数据转换为 ECharts 格式：

    chart_config[0]: { type: "pie", title: "各厂商市场份额",
                       name_field: "entity_name",
                       value_field: "avg_market_share" }

    生成的图表数据:
    {
      "type": "pie",
      "title": "各厂商市场份额",
      "data": [
        {"name": "Siemens", "value": 35.2},
        {"name": "Rockwell", "value": 24.8},
        ...
      ]
    }
    ─────────────────────────────────────────────────────────
    │
    ▼
[4. 渲染 Prompt]
    Jinja2 渲染 prompt_template（含聚合数据变量）

    变量:
    {{ chart_data }}   ← 上面生成的图表数据 JSON
    {{ record_count }} ← 参与聚合的事实条数
    {{ start_date }}   ← now() - lookback_days
    {{ end_date }}     ← now()
    {{ aggregate_data }} ← 原始聚合数据
    ─────────────────────────────────────────────────────────
    │
    ▼
[5. LLM 生成文字总结]（60s 超时）
    注意：此处的 LLM 调用只负责"文字总结"，不涉及逻辑推理
    Prompt 明确要求：不虚构数据，只描述已有数据

    ┌────────────────────────────────────────────────────┐
    │ Prompt 内容示例:                                     │
    │                                                       │
    │ 你是情报分析师。请基于以下已聚合的市场数据，             │
    │ 撰写一段 200-300 字的市场分析摘要。                     │
    │                                                       │
    │ 数据范围：2026-07-12 至 2026-08-11                   │
    │ 参与分析的事实数：156 条                               │
    │                                                       │
    │ 【数据图表】                                          │
    │ {chart_data_json}                                    │
    │                                                       │
    │ 要求：                                                 │
    │ - 不虚构数据，只描述已有数据                            │
    │ - 不少于 200 字                                       │
    │ - 提供一段话总结                                      │
    │                                                       │
    │ 按 JSON 返回：                                         │
    │ {                                                      │
    │   "analysis": "文字分析...",                            │
    │   "summary": "一段话总结..."                           │
    │ }                                                      │
    └────────────────────────────────────────────────────┘
    │
    ▼
[6. 存入 report_run 表]
    aggregated_data = [SQL 聚合结果]
    output_analysis = {LLM 返回的分析文字}
    output_charts   = [图表数据]
    output_summary  = {LLM 返回的总结}
    │
    ▼
[7. 更新模板状态]
    UPDATE intel_aggregate SET next_run = now() + schedule_minutes
    reset fail_count
    │
    ▼
[完成]
```

## 7. Prompt 系统

### 7.1 抽取 Prompt（用于情报结构化）

**设计原则：**
- 每次调用只抽取一个规则的字段
- 严格 JSON 输出格式
- 找不到字段填 null，不虚构
- 60s 超时（比报告分析短）

**系统 Prompt（固定）：**

```
你是一个专业的情报数据提取员。你的任务是从文本中提取指定字段的数据。

重要规则：
1. 只提取文本中明确提到的信息，不要推断或虚构
2. 找不到的字段填 null
3. 严格按 JSON 格式返回，不要包含任何其他内容
4. 数值字段请提取为数字（不是字符串）
5. 如果文本中提到多个实体（如多家公司），只提取第一个出现的完整记录
```

**用户 Prompt（动态生成）：**

```jinja2
请从以下情报文本中提取以下字段的数据：

【抽取规则】{{ rule_name }}

【字段定义】
{% for field in fields %}
- {{ field.field_key }}（{{ field.field_label }}）：类型为 {{ field.field_type }}{% if field.is_required %}，必填{% endif %}
{% endfor %}

【情报标题】{{ intel_title }}

【情报内容】
{{ intel_content }}

请严格按以下 JSON 格式返回（字段顺序与定义一致）：
{
{% for field in fields %}
  "{{ field.field_key }}": null,
{% endfor %}
}
```

### 7.2 报告分析 Prompt（用于报告文字总结）

**设计原则：**
- LLM 只负责"文字描述已有数据"，不涉及逻辑推理
- 数据由 SQL 聚合生成，LLM 不接触原始情报
- 120s 超时
- 明确禁止虚构数据

**系统 Prompt（固定）：**

```
你是专业情报分析师。请基于已聚合的数据，撰写市场分析报告。

重要规则：
1. 只描述已有数据，不要推断或虚构任何信息
2. 所有数据来自 JSON 格式提供的聚合结果
3. 报告应有逻辑结构，先总后分
4. 语言简洁专业
5. 严格 JSON 格式返回
```

**用户 Prompt（动态生成）：**

```jinja2
【报告名称】{{ report_name }}
【分析范围】{{ start_date }} 至 {{ end_date }}
【参与分析的数据】{{ fact_count }} 条结构化事实

=== 数据聚合结果 ===
{{ aggregated_data }}

=== 图表数据 ===
{{ chart_data }}

请基于以上数据撰写分析报告，按 JSON 格式返回：
{
  "analysis": "文字分析内容（不少于 200 字）...",
  "summary": "一段话总结（30-50 字）..."
}
```

| 参数 | 值 | 说明 |
|------|-----|------|

| LLM max_tokens | 抽取: 500 / 报告: 1500 | 限制输出长度 |

## 10. 风险与缓解

| 风险 | 影响 | 概率 | 缓解措施 |
|------|------|:----:|----------|
| LLM 持续不可用 | 情报无法抽取，报告无新数据 | 中 | 抽取任务自动重试；报告保留已有聚合数据继续运行 |
| 抽取 Prompt 被恶意内容干扰 | 抽取结果错误 | 低 | 使用 `StrictUndefined`；抽取结果标记 `confidence`；允许手动修正 |
| 用户规则定义不规范 | 抽取结果质量低 | 中 | 字段类型强约束（`company` 只能存 entity_name）；置信度标记 |
| 一条情报同时匹配多个规则 | 事实重复 | 低 | `intel_fact` 有 `rule_id` 区分来源，报告按 `rule_id` 查询 |
| 抽取 JSON 格式错误 | 抽取失败 | 中 | 解析失败标记 `extracted = failed`，下次重试；限制 `max_tokens=500` |
| SQLite 写锁竞争 | 调度器写入失败 | 低 | 抽取和报告串行执行；Flask 不写入新表 |
| 报表需求持续变化 | 用户频繁改配置 | 设计内 | 所有配置存数据库，前端表单编辑，无需改代码 |
| 内置规则与自定义规则冲突 | 数据重复抽取 | 低 | 两条规则分别产生 `intel_fact`，`rule_id` 区分；报告按 `rule_id` 查询 |

### B. 与 v1.0 的关键差异

| 设计点 | v1.0 | v1.1 | 原因 |
|--------|------|------|------|
| 数据基础 | 从 `content` 文本推理 | 从 `intel_fact` 结构化数据聚合 | 原文本无法支撑聚合查询 |
| LLM 职责 | 推理主体 | 抽取工具 + 文字总结工具 | 降低 LLM 任务复杂度 |
| 报告生成 | LLM 生成全部（文字+图表数据） | SQL 聚合生成图表数据 + LLM 生成文字 | 图表数据来自 SQL，不依赖 LLM |
| 新增表 | 3 张 | 7 张 | 四层架构需要更多支撑 |
| 前端页面 | 2 页（reports + report-view） | 3 页（加 intel-extract） | 抽取规则管理需要独立页面 |
| 调度流程 | 单流程（报告生成） | 双流程（抽取 + 报告） | 抽取是报告的前置步骤 |
| 灵活度 | 中等 | 高（所有配置可前端修改） | 应对"报表需求多变" |

### C. 架构决策记录（ADR）

**ADR-001：为什么选择 key-value 混合的 intel_fact 表而非宽表**

> 决策：`intel_fact` 使用固定字段（`field_key` + `entity_name` + `metric_value`）的 key-value 模式，而非为每个可能的指标创建一个列的宽表模式。
>
> 理由：报表需求多变，不可能预先知道所有需要的指标。宽表需要频繁 ALTER TABLE，key-value 模式零 Schema 变更。
>
> 代价：多字段过滤时需要 self-join，增加查询复杂度。通过索引和 SQLite 优化可以接受。

**ADR-002：为什么抽取放在系统内而非外部 Agent 侧**

> 决策：结构化抽取放在系统调度器中执行，而非修改外部 AI Agent 的采集流程。
>
> 理由：外部 Agent 的修改不在本项目的控制范围内，依赖外部团队的配合。系统内抽取可以随时调整规则，无需等待外部改动。
>
> 代价：抽取需要额外调用 LLM，增加服务器负载。但抽取任务简单，单次 60s 超时足够。
